压力测试调试日志：从工具链崩溃到原生 Socket 的实现之路

概述

在对 ESP32 Modbus TCP 从站进行压力测试的过程中，工具链的意外失败迫使我回归通信协议的本质。本文档记录了从发现问题到最终实现的完整决策过程。

第一阶段：工具链失效

1.1 Modbus Poll 连接失败

现象

Modbus Poll 持续报 Timeout error 和 Write error

Windows 防火墙已放行 502 端口

Ping 测试正常，网络层通畅

诊断

检查了所有常规配置项（IP、端口、协议类型）均无误。在消耗 1.5 小时后，判断为工具在特定环境下的兼容性问题，决定切换到脚本方案。

1.2 pymodbus 版本陷阱

现象

切换到 Python 脚本后：

from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('192.168.1.100', port=502)

出现 ImportError 及参数错误。

诊断

当前环境安装的是 pymodbus 2.5.0（旧版）

新版 3.x API 已变更，升级后语法不兼容

尝试降级适配，但仍有隐性报错

决策

在单一问题上已消耗 2 小时，遵循“工业现场效率优先”原则，放弃对第三方库的调试，采用最底层的解决方案。

第二阶段：回归本质

2.1 选择原生 Socket

理由

完全可控：无需依赖外部库版本

协议透明：可逐字节查看通信过程

零依赖部署：仅需 Python 标准库

工业适配性：可灵活应对非标准 Modbus 变种

2.2 实现核心

Modbus TCP 帧结构手动构造

request = struct.pack('>HHHBBHH',

transaction_id,  # 事务ID（自增）

0,               # 协议ID（Modbus固定为0）

6,               # 后续字节长度

unit_id,         # 单元ID（设备地址）

0x03,            # 功能码：读保持寄存器

address,         # 起始地址

count            # 寄存器数量

)

关键点

大端字节序（>）

固定协议头长度：7 字节

事务 ID 用于请求-响应匹配

第三阶段：压力测试实现

3.1 基础读取验证

创建 raw_test.py，实现单次读取功能。首次运行即成功获取寄存器数据，验证了协议的准确性。

3.2 压力测试扩展

在 raw_test.py 基础上创建 stress_test.py：

添加循环结构（20 次迭代）

记录每次请求的起止时间

统计成功/失败次数

控制请求间隔（200ms）

3.3 测试结果

测试轮次 成功率 平均响应时间 网络状况

第一次 40% 约 150ms WiFi 有波动

第二次 100% 约 50ms 网络稳定

经验总结

4.1 技术层面

工具不可靠：工业环境中，标准工具可能因驱动、版本、环境配置等原因失效

协议是根本：掌握协议帧结构（事务 ID、协议 ID、长度字段）可自主解决 90% 通信问题

分层排查：

网络层：Ping 测试

传输层：端口/防火墙

应用层：协议/工具

4.2 工程思维

时间管理：单个问题超过 2 小时无实质进展，立即切换方案

降级能力：具备从“库”到“协议”的降级实现能力

数据驱动：用成功率、响应时间等量化指标评估方案

4.3 工业现场适配

本次调试模拟了工业现场的典型约束：

不可随意升级/降级系统组件

网络环境不稳定

需要快速解决问题而非完美方案
